# 功能演示指南

5 分钟走完本项目的四个核心能力：RAG 问答、检索开关对照、工具调用、写操作二次确认。
每一步都标了「操作」和「能看到什么」。

---

## 演示前 3 分钟准备

### 方式一：一键启动（推荐，不依赖 IDE）

```bash
# 先手动启动 Docker Desktop（开始菜单点一下，等托盘图标变绿）
cd ai-customer-agent
bash start.sh --reset-demo        # 首次跑再加上 --rebuild
```

脚本会依次：起数据库容器 → 起后端 jar → 起前端 preview，最后打印

```
  演示环境已就绪
  应用入口    http://127.0.0.1:4173
  登录账号    admin / admin123
```

**浏览器打开 `http://127.0.0.1:4173`** 即可（注意是 **4173**，不是 5173）。

- 首次运行会自动打包前后端，约 1 分钟；产物存在则跳过
- 改过代码要重新打包：`bash start.sh --rebuild`
- 结束时在脚本窗口按 `Ctrl+C`，它会自动停掉 8080 和 4173 两个进程

### 方式二：开发模式（需要改代码、要热更新时）

```bash
docker compose up -d
cd backend  && mvn spring-boot:run     # 8080
cd frontend && npm run dev             # 5173
```

两种方式的差别只有前端端口（4173 preview / 5173 dev）。

### 开演前检查三件事

- [ ] **`ready: true`**（说明两个 API Key 都配好了）
      `bash start.sh` 的输出里会打 `✓ 后端就绪`；也可手动 `curl -s http://127.0.0.1:8080/api/chat/status`
- [ ] **知识库有 8 篇文档、20 个切片**（登录后进 `/kb` 页面直接看）
- [ ] **订单 `202610010001` 是「已发货」**（不是「退款中」，
      否则场景 D 的退款演示会变成「重复申请被拒」）

`--reset-demo` 会把演示订单恢复到初始状态（取值来自 `db/02-seed.sql`）。
服务已在跑、不想重启时，也可以直接执行：

```bash
docker exec agent-postgres psql -U agent -d agent_db -c \
  "UPDATE mock_order SET status='已发货' WHERE order_no='202610010001';
   UPDATE mock_order SET receiver_address='广州市天河区体育西路 12 号维多利广场 B 塔 903'
     WHERE order_no='202610010005';"
```

> 地址要连着一起还原：场景 E 演示的就是修改这条地址，
> 不还原的话第二次演示看不出「修改前 → 修改后」的变化。

## 演示操作的三个前提

1. **示例问题按钮只在「空对话」时出现。** 首页那四个卡片（`退款一般几天到账？` 等）
   一旦发出第一条消息就消失了。
2. **所以每切换一个场景前，点一次输入框右上角的「清空对话」。**
   它会同时重置会话上下文、清空右侧面板、把示例卡片放回来 ——
   每个场景都从干净状态开始，右侧面板的轨迹也更好读。
3. 后面的问题也可以直接在输入框打字（`Enter` 发送、`Shift+Enter` 换行），
   演示时用「清空对话 + 点示例卡片」更快。

> 决策面板是按**每轮**重置的，不是累积的 —— 这也是设计意图：
> 每一轮问答独立展示一次完整的决策轨迹。

## 一、开场（30 秒）

**打开** `http://127.0.0.1:4173`，停在登录页，登录 `admin / admin123`。

先不提问，看一眼右侧决策面板的空状态。每问一个问题，它会实时显示 Agent 做了什么：
检索命中了什么、每条相似度多少、调了哪个工具、参数是什么、每步耗时多少。

---

## 二、场景 A：纯知识库问答（1 分钟）

**操作**：点第一张示例卡片 → 「退款一般几天到账？」

**能看到**：

- 回答逐字流式输出，带表格
- 数字后面有蓝色角标 `[1]` `[2]`
- 回答下方有「引用来源」卡片，显示文档名和相似度
- 右侧面板：检索耗时、5 条命中的分数条、每条的片段

**技术要点**：

- 分数条上红竖线是阈值 0.55，超过阈值的才送进 Prompt（标「已送入 Prompt」），
  不够的标「分数不足，已丢弃」
- **检索层不负责过滤**：它返回全部 topK 命中和分数，过滤推迟到 Prompt 组装那一步。
  这样模型说「我查不到」时，能分清是「检索没召回」还是「召回了但分数不够」，
  两种故障在观测上是不同的
- 阈值由 `scripts/eval-retrieval.py` 实测确定（15 个标注问题 + 4 个知识库外问题）：

| 阈值 | 答案覆盖率 | 噪声率 | 正确拒答率 |
|---|---|---|---|
| 0.35（原配置） | 100% | 75.3% | **0%** |
| 0.50 | 100% | 73.1% | 25% |
| **0.55（现配置）** | **100%** | **69.8%** | **100%** |
| 0.60 | 100% | 61.8% | 100% |

  真问题的 Top1 最低分 0.632，知识库外问题最高分 0.522，分界线在 0.55 附近。

## 三、场景 B：关掉检索做对照（1 分钟）

**操作**：

1. 点「清空对话」
2. 关掉输入框上方的「知识库检索」开关
3. 点第一张示例卡片（问同一个问题）

**能看到**：模型仍然回答了，但数字可能不一样，或者开始含糊其辞；
右侧面板的检索区是空的，模型没有任何依据。

**技术要点**：关掉检索后模型只能凭训练数据回答。电商政策这类强时效内容，
它给的数字不可信 —— 这就是 RAG 的价值：**不是让模型更聪明，是让它有据可依**。

**演示完重新打开「知识库检索」开关。**

---

## 四、场景 C：只读工具调用（1 分钟）

**操作**：点「清空对话」→ 点第二张示例卡片 → 「帮我查一下订单 202610010003 的物流到哪了」

**能看到**：

- 右侧面板出现「工具调用」时间线
- `查询物流 query_logistics` + 参数 + 「成功」徽标 + 耗时
- 「决策轮数 2」「工具调用 1」

**技术要点**：

- 决策轮数是 2：第一轮模型判断需要查物流，自己生成工具调用和参数；
  工具返回之后，第二轮才基于真实数据组织回答
- 订单号是问题里给的。如果不给，模型不会编造，而是先询问订单号 ——
  这个约束写在工具描述里，**工具描述本身就是 Prompt 的一部分**
- 与纯 RAG 的本质区别：纯 RAG 的流程是固定的（检索、拼 prompt、生成），
  这里模型要自己决定要不要调工具、调哪个、参数是什么、结果够不够

## 五、场景 D：写操作二次确认（1.5 分钟，**重点**）

**操作**：点「清空对话」→ 点第三张示例卡片 → 「订单 202610010001 我要退款，商品有质量问题」

**能看到**：

1. 右侧面板出现 `query_order` 然后又出现 `apply_refund`，标着橙色「写操作」
2. 中间弹出确认框：「为订单 202610010001 提交退款申请，退款原因：商品有质量问题」
3. 弹窗底部有 60 秒倒计时进度条
4. 点「确认执行」后，工具返回，模型继续流式输出

**技术要点**（弹窗出现时可先讲解再点确认）：

- 模型已决定调用 `apply_refund`，但这是写操作，**SSE 流在此挂起**。
  「挂起」和「唤醒」在两个完全独立的请求里：推流线程阻塞等待，
  用户点击走的是另一个 HTTP 请求 `POST /api/chat/confirm` —— 不同连接、不同线程。
  进程内维护 `ConfirmRegistry`，用 `confirmId` 把两者接起来
- 挂起时**不能关闭 SseEmitter**：关了前端就收不到后续内容。
  所以保留流、把 `confirmId → SseEmitter` 存进注册表，等回执来了再继续推
- 三个必须处理的边界：
  1. **超时** —— 60 秒自动取消，不能让推流线程永久阻塞（线程池只有 16 个）
  2. **重复点击** —— CAS 保证只有第一个回执生效，后续返回「已失效」
  3. **迟到回执** —— 已超时后点击，CAS 失败回「已失效」而不是偷偷改成确认；
     **一旦判定超时就不能被推翻**

**点「确认执行」后**，可切到数据库验证真实落库：

```bash
docker exec agent-postgres psql -U agent -d agent_db -c \
  "SELECT order_no, status FROM mock_order WHERE order_no='202610010001';"
```

结果应为 `退款中` —— 工具执行的是真实的 update，不是模拟。

## 六、场景 E：取消路径（30 秒）

**操作**：点「清空对话」→ 点第四张示例卡片 → 「把订单 202610010005 的收货地址改成杭州市西湖区文三路 100 号」→ 弹窗出现时点「取消」

**能看到**：右侧工具卡片状态变成灰色「已取消」，模型回答「操作已取消，地址未做任何变更」。

可验证地址确实没变：

```bash
docker exec agent-postgres psql -U agent -d agent_db -c \
  "SELECT order_no, receiver_address FROM mock_order WHERE order_no='202610010005';"
```

**技术要点**：取消结果回灌给模型时，明确写了「请直接告知用户操作已取消，
不要再次尝试调用该工具」—— 否则模型可能原地再发起一次同样的调用。
**给模型的错误信息里要包含「下一步该做什么」，而不只是「哪里错了」**。

## 七、收尾：讲架构（30 秒）

**打开** `docs/技术设计说明.md` 的架构图，或直接口述：

- 前端三个页面（登录 / 对话+决策面板 / 知识库），后端三层：接口层、Agent 编排、RAG 和工具层
- 数据库用 PostgreSQL + pgvector，向量和业务数据放一起，省一个中间件
- 两个主动的取舍：
  1. **没用 LangChain4j / Spring AI** —— 编排逻辑本身是这个项目的核心，
     用框架会把 Agent 循环、流式工具解析、工具注册全部封装掉
  2. **工具调用走流式而不是「先非流式决策再流式生成」** ——
     后者代码简单得多，但每个不需要工具的普通问答都会多一次非流式往返，
     首 token 延迟直接翻倍。所以自己解析了流式的 tool_calls 分片

## 故障预案

| 现象 | 处理 |
| --- | --- |
| 端口 8080 或 4173 已被占用 | `start.sh` 会在启动前就报错退出。找占用者：`netstat -ano \| findstr :8080`，然后 `taskkill /F /PID <pid>` |
| 后端起不来 | 看日志 `/tmp/agent-backend.log`；确认 Docker Desktop 已启动 |
| 前端打开是白屏 / 接口 404 | 多半是 `frontend/dist` 是旧的，`bash start.sh --rebuild` |
| 数据库连不上 | `docker ps` 看容器；宿主机端口是 **15433** 不是 5433 |
| 提示 API Key 未配置 | 检查 `backend/src/main/resources/application-local.yml`，或看 `curl /api/chat/status` 里的 `llmConfigured` / `embeddingConfigured` |
| 回答里出现「重复申请被拒」 | 订单已经是「退款中」了，用开头的 SQL 重置 |
| 检索结果为空 | 确认知识库里有文档（`/kb` 页）；阈值是 0.55，分数不够会被标为「已丢弃」 |
| 弹窗出现后一直没点，模型卡住 | 60 秒后自动取消，这是预期行为。想快点了就按「取消」 |
