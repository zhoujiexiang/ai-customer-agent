# 演示脚本（5 分钟版）

面试或录屏时按这个流程走。每一步都标了「要说什么」和「对方会看到什么」。

---

## 演示前 3 分钟准备

### 方式一：一键启动（推荐，不依赖 IDEA）

```bash
# 先手动启动 Docker Desktop（开始菜单点一下，等托盘图标变绿）
cd ai-customer-agent
bash start.sh --reset-demo        # 首次跑再加上 --rebuild
```

脚本会依次：起数据库容器 → 起后端 jar → 起前端 preview，最后打印

```
  演示环境已就绪
  应用入口    http://127.0.0.1:4173
  登录账号    admin / admin123
```

**浏览器打开 `http://127.0.0.1:4173`** 即可（注意是 **4173**，不是 5173）。

- 首次运行会自动打包前后端，约 1 分钟；产物存在则跳过
- 改过代码要重新打包：`bash start.sh --rebuild`
- 结束时在脚本窗口按 `Ctrl+C`，它会自动停掉 8080 和 4173 两个进程

### 方式二：开发模式（需要改代码、要热更新时）

```bash
docker compose up -d
cd backend  && mvn spring-boot:run     # 8080
cd frontend && npm run dev             # 5173
```

两种方式的差别只有前端端口（4173 preview / 5173 dev）。**预演时用方式一**，
构建产物没有 HMR 干扰，也不会因为改代码触发重载。

### 开演前检查三件事

- [ ] **`ready: true`**（说明两个 API Key 都配好了）
      `bash start.sh` 的输出里会打 `✓ 后端就绪`；也可手动 `curl -s http://127.0.0.1:8080/api/chat/status`
- [ ] **知识库有 8 篇文档、20 个切片**（登录后进 `/kb` 页面直接看）
- [ ] **订单 `202610010001` 是「已发货」**（不是「退款中」，
      否则场景 D 的退款演示会变成「重复申请被拒」）

重置演示数据（**每次演示前都做一遍**，保证可重复）：

- 服务还没起：`bash start.sh --reset-demo` 一步到位（见上面的方式一）
- 服务已经在跑：直接执行下面的 SQL，不用重启

（值取自 `db/02-seed.sql`，别凭记忆写）

```bash
docker exec agent-postgres psql -U agent -d agent_db -c \
  "UPDATE mock_order SET status='已发货' WHERE order_no='202610010001';
   UPDATE mock_order SET receiver_address='广州市天河区体育西路 12 号维多利广场 B 塔 903'
     WHERE order_no='202610010005';"
```

> 为什么连地址一起还原：场景 E 改的就是 005 的地址。不还原的话，
> 第二次演示时「修改前 → 修改后」的对比就看不出来了 —— 地址已经是对的了。
> **这条不在文档里写清楚，下次就会凭印象编一个地址，把演示数据改坏。**（踩过）

## 演示操作的三个前提（重要）

1. **示例问题按钮只在「空对话」时出现。** 首页那四个卡片（`退款一般几天到账？` 等）
   一旦发出第一条消息就消失了。
2. **所以每切换一个场景前，点一次输入框右上角的「清空对话」。**
   按钮小，但它会同时重置会话上下文、清空右侧面板、把示例卡片放回来 ——
   每个场景都从干净状态开始，右侧面板的轨迹也更好读。
3. 后面的问题也可以直接在输入框打字（`Enter` 发送、`Shift+Enter` 换行），
   演示时用「清空对话 + 点示例卡片」更快，不用现场打字。

> 如果面试官问「为什么一直清空」：答「让每一轮都独立展示决策面板」，
> 这本身也是设计意图 —— 面板是按**每轮**重置的，不是累积的。

## 一、开场（30 秒）

**打开** `http://127.0.0.1:4173`，停在登录页。

> 「这是一个电商售后客服 Agent。左边是对话，右边是 Agent 的决策面板 ——
> 我待会儿会重点讲右边这个，因为它是这个项目跟普通 RAG 问答最大的区别。
> 先登录。」

登录 `admin / admin123`，停在对话页。**不要急着提问**，先让对方看一眼右侧面板的空状态。

> 「右侧面板现在是空的。每问一个问题，它会实时显示 Agent 做了什么：
> 检索命中了什么、每条相似度多少、调了哪个工具、参数是什么、每步耗时多少。」

## 二、场景 A：纯知识库问答（1 分钟）

**点第一张示例卡片** → 「退款一般几天到账？」

**对方看到**：

- 回答逐字流式输出，带表格
- 数字后面有蓝色角标 `[1]` `[2]`
- 回答下方有「引用来源」卡片，显示文档名和相似度
- 右侧面板：检索耗时、5 条命中的分数条、每条的片段

**要说的**：

> 「注意右边这个分数条 —— 每条命中都有一个分数，红竖线是阈值 0.55。
> 超过阈值的才会被送进 Prompt，片段下面会标『已送入 Prompt』；不够的标『分数不足，已丢弃』。」

> 「这里有个设计决定值得说：**检索层不负责过滤**。它返回全部 topK 命中和分数，
> 过滤推迟到 Prompt 组装那一步。为什么？因为模型说『我查不到』的时候你得分清是
> 检索没召回，还是召回了但分数不够。如果检索层直接扔了，这两种情况在观测上完全一样。」

> 「这个阈值不是拍的，是**测出来的**。我写了评测脚本，15 个标注问题 + 4 个知识库外的问题扫一遍：
>
> | 阈值 | 答案覆盖率 | 噪声率 | 正确拒答率 |
> |---|---|---|---|
> | 0.35（原配置） | 100% | 75.3% | **0%** |
> | 0.50 | 100% | 73.1% | 25% |
> | **0.55（现配置）** | **100%** | **69.8%** | **100%** |
> | 0.60 | 100% | 61.8% | 100% |
>
> 两条线很干净：真问题的最高分最低是 **0.632**，知识库外问题的最高分只有 **0.522**，
> 中间这条线就在 0.55 附近。原来 0.35 时正确拒答率是 0%，调到 0.55 变成 100%，
> 而答案覆盖率一点没掉。」

> **（如果对方追问「为什么不干脆用 0.60，噪声更低？」——这是个好问题）**
>
> 「脚本按『覆盖率 − 噪声 × 0.5』自动打分，推荐的其实是 0.60。但我选了 0.55，原因是
> **那个评分函数只惩罚噪声，没建模误杀风险**。0.60 时，正确命中的最低分 0.632
> 距离阈值只剩 0.03 的余量；0.55 留了 0.08。用户换一种不规范的问法，分数很可能会下探，
> 0.60 就开始误杀了。所以我用自动推荐做参考、用人来判断安全边际 ——
> **自动化评测能告诉你曲线在哪，但不能替你决定愿意承担多大的误杀风险。**」

## 三、场景 B：关掉检索做对照（1 分钟）

1. **点「清空对话」**
2. **关掉输入框上方的「知识库检索」开关**
3. **点第一张示例卡片**（问同一个问题）

**对方看到**：模型仍然回答了，但数字可能不一样，或者开始含糊其辞。

**要说的**：

> 「关掉检索之后，模型只能凭训练数据里的常识回答。电商政策这种强时效的东西，
> 它给的数字就不可信了。这就是 RAG 存在的理由 ——
> **不是让模型更聪明，是让它有据可依**。」

> （指着右侧面板）「你看右边，检索那一块现在是空的，模型没有任何依据。
> 这时候它说的话，和我刚才给你看的带引用的回答，可信度是完全不同的。」

**重新打开「知识库检索」开关。**

## 四、场景 C：只读工具调用（1 分钟）

1. **点「清空对话」**
2. **点第二张示例卡片** → 「帮我查一下订单 202610010003 的物流到哪了」

**对方看到**：

- 右侧面板出现「工具调用」时间线
- `查询物流 query_logistics` + 参数 + 「成功」徽标 + 耗时
- 「决策轮数 2」「工具调用 1」

**要说的**：

> 「这一轮和刚才不一样了。**决策轮数是 2** —— 第一轮模型判断需要查物流，
> 它自己生成了工具调用和参数；工具返回之后，第二轮它才基于真实数据组织回答。」

> 「订单号是我在问题里给的。如果我不给，它不会瞎编一个，而是会先问我要订单号 ——
> 这个约束写在工具描述里，因为**工具描述本身就是 Prompt 的一部分**。」

**这时可以主动补一句**：

> 「这是它和纯 RAG 的本质区别：纯 RAG 的流程是固定的，检索、拼 prompt、生成。
> 这里的模型要自己决定：要不要调工具、调哪个、参数是什么、拿到结果够不够。」

## 五、场景 D：写操作二次确认（1.5 分钟，**这是重点**）

1. **点「清空对话」**
2. **点第三张示例卡片** → 「订单 202610010001 我要退款，商品有质量问题」

**对方看到**：

1. 右侧面板出现 `query_order` 然后又出现 `apply_refund`，标着橙色「写操作」
2. **中间弹出确认框**：「为订单 202610010001 提交退款申请，退款原因：商品有质量问题」
3. 弹窗底部有 60 秒倒计时进度条
4. 点「确认执行」后，工具返回，模型继续说

**先用手指着弹窗，别急着点**：

> 「停一下，看这个弹窗。模型已经决定要调 `apply_refund` 了，
> 但这是一个会改数据的操作，所以 **SSE 流在这里挂起了**。」

> 「技术上这是整个项目最麻烦的一块，因为『挂起』和『唤醒』在两个完全独立的请求里：
> 推流线程阻塞在这个弹窗上等，用户点击走的是另一个 HTTP 请求 `POST /api/chat/confirm`。
> 两者之间没有任何天然关联 —— 不同的连接、不同的线程。
> 我在进程里维护了一个 `ConfirmRegistry`，用 `confirmId` 把它们接起来。」

> 「还有个细节：**挂起时不能关闭 SseEmitter**，关了前端就收不到后续内容了。
> 所以我保留流、把 `confirmId → SseEmitter` 存进注册表，等回执来了再 `send()` 继续推。」

**点「确认执行」**，然后切到数据库验证：

```bash
docker exec agent-postgres psql -U agent -d agent_db -c \
  "SELECT order_no, status FROM mock_order WHERE order_no='202610010001';"
```

**对方看到**：`202610010001 | 退款中`

**要说的**：

> 「数据真的改了。这不是模拟的，工具执行的就是真实的 update。」

**然后主动说三个边界**（这段是加分项）：

> 「这里有三个必须处理的边界。**第一是超时** —— 用户不点怎么办？
> 60 秒自动取消。关键是**不能让推流线程永久阻塞**，我的线程池只有 16 个，
> 几个人挂机就能把服务拖垮。」

> 「**第二是重复点击** —— 用户连点两下，或者开两个标签页各点一次。
> 我用一次 CAS 保证只有第一个回执生效，第二次直接返回『已失效』。」

> 「**第三是迟到回执** —— 已经超时之后用户才点。CAS 会失败，接口回『已失效』，
> 而不是偷偷把状态改成确认。**一旦判定超时就不能被推翻**，这个顺序保证很重要。」

## 六、场景 E：取消路径（30 秒）

1. **点「清空对话」**
2. **点第四张示例卡片** → 「把订单 202610010005 的收货地址改成杭州市西湖区文三路 100 号」
3. 弹窗出现时**点「取消」**

**对方看到**：右侧工具卡片状态变成灰色「已取消」，模型回答「操作已取消，地址未做任何变更」。

可以顺手验证地址确实没变：

```bash
docker exec agent-postgres psql -U agent -d agent_db -c \
  "SELECT order_no, receiver_address FROM mock_order WHERE order_no='202610010005';"
```

**要说的**：

> 「取消之后工具没有执行。这里有个细节：我把取消的原因回灌给模型的时候，
> 明确写了『请直接告知用户操作已取消，**不要再次尝试调用该工具**』。
> 不加这句，模型很可能原地再发起一次同样的调用，然后又被拒绝，白白烧两轮 token。
> **给模型的错误信息里要包含『下一步该做什么』，而不只是『哪里错了』**。」

## 七、收尾：讲架构（30 秒）

**打开** `docs/技术设计说明.md` 的架构图，或者直接口述。

> 「整体是前端两个页面，后端三层：接口层、Agent 编排、RAG 和工具层。
> 数据库用 PostgreSQL 加 pgvector，向量和业务数据放一起，省了一个中间件。」

> 「有两个地方是我主动做了取舍的。**一个是没用 LangChain4j 或 Spring AI** ——
> 这个项目要展示的恰好是编排逻辑本身，用框架会把 Agent 循环、流式工具解析、
> 工具注册全部封装掉，面试时说不清里面发生了什么。」

> 「**另一个是工具调用走了流式而不是『先非流式决策再流式生成』**。
> 后者代码简单得多，但每个不需要工具的普通问答都会多一次非流式往返，
> 首 token 延迟直接翻倍。所以我自己解析了流式的 tool_calls 分片。」

## 如果对方追问

| 问题 | 回答要点 |
| --- | --- |
| **这个能支持多实例吗？** | 现在不行，`ConfirmRegistry` 是进程内的 ConcurrentHashMap。多实例下用户点确认可能落到另一台机器上找不到挂起的流。要支持得换 Redis + 发布订阅。**主动承认这个限制**比装作没问题可信 |
| **数据量大了怎么办？** | 现在几十到几万个切片用精确的 `<=>` 全表扫描够了，schema 里已经预留了 HNSW 索引的建表语句，注释掉了。再往上要考虑 Milvus，但那是数据量驱动的问题 |
| **怎么防止模型乱调工具？** | 三层：工具描述里写清使用场景和前置条件、JSON Schema 限死参数、执行前校验参数并在失败时返回明确错误让模型重新决策 |
| **模型调工具失败会怎样？** | 不中断对话，把失败作为工具结果回灌，让它换方式回答。刚才场景里订单不存在时会说「没查到，请确认订单号」 |
| **模型反复调工具死循环呢？** | `MAX_AGENT_STEPS = 5` 硬上限。跑满之后去掉 tools 再跑一次，强制它基于已有信息生成文字回答，保证用户至少拿到一个可读结果 |
| **首 token 为什么有时候 2 秒？** | 调工具的那些轮次首 token 天然更慢，因为要等模型决策 + 工具执行 + 第二轮生成。**多步能力的代价就是首字延迟** —— 这是必须向用户交代的取舍 |
| **做了 RAG 效果评测吗？** | 做了，`scripts/eval-retrieval.py`，跑一次 21 秒。**Hit@1 = 15/15 = 100%，Hit@3 100%，MRR = 1.0000**；真问题 Top1 分数 min 0.632 / 平均 0.737 / max 0.813，知识库外问题最高分 0.522。阈值 0.55 就是这么定出来的 |
| **做过混合检索吗？** | 做过也评测过，**结论是不落地**。等权 RRF 把向量通道的 MRR 从 0.9000 打到 0.6135，原因可以推导：向量第 1 名得 `w_v/(k+1)`，而「向量第 2 名 + 关键词第 1 名」的共识候选得 `w_v/(k+2)+w_k/(k+1)`，反超条件是 `w_k > w_v/(k+2)`，k=60 时只有 **1.6%**。实测 0.99/0.01 保住 0.9000、0.98/0.02 掉到 0.8375，正好卡在临界点两侧。**任何有效权重都远在线上，所以调权重是伪选项。** 关键词通道保留为降级/调试用（`?mode=keyword`），理由不是精度而是：快、不依赖外部 Embedding 服务、Embedding 挂了它是唯一退路 |

## 故障预案

| 现象 | 处理 |
| --- | --- |
| 端口 8080 或 4173 已被占用 | `start.sh` 会在启动前就报错退出。找占用者：`netstat -ano \| findstr :8080`，然后 `taskkill /F /PID <pid>` |
| 后端起不来 | 看日志 `/tmp/agent-backend.log`；确认 Docker Desktop 已启动 |
| 前端打开是白屏 / 接口 404 | 多半是 `frontend/dist` 是旧的，`bash start.sh --rebuild` |
| 数据库连不上 | `docker ps` 看容器；宿主机端口是 **15433** 不是 5433 |
| 提示 API Key 未配置 | 检查 `backend/src/main/resources/application-local.yml`，或看 `curl /api/chat/status` 里的 `llmConfigured` / `embeddingConfigured` |
| 回答里出现「重复申请被拒」 | 订单已经是「退款中」了，用开头的 SQL 重置 |
| 检索结果为空 | 确认知识库里有文档（`/kb` 页）；阈值是 0.55，分数不够会被标为「已丢弃」 |
| 弹窗出现后一直没点，模型卡住 | 60 秒后自动取消，这是预期行为。想快点了就按「取消」 |
