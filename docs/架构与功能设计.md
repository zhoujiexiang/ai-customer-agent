## 六、★ 二次确认交互设计（本版核心难点）

写操作是这一版最有技术含量的部分，因为它涉及 **SSE 流的中断与恢复**。

### 交互流程

```
1. 用户：「帮我退了这单」
2. 模型决策：需要调用 apply_refund
3. 后端【不执行】，推送 tool_confirm 事件：
     { name: "apply_refund", args: {orderNo: "20261001001"}, needConfirm: true }
4. 前端渲染确认卡片：「确认申请退款？订单 20261001001，金额 ¥299」
     [确认]  [取消]
5. 后端挂起当前 SSE 流（SseEmitter 不关闭），等待回执，设 60 秒超时
6. 用户点「确认」→ 前端 POST /api/chat/confirm { messageId, approved: true }
7. 后端唤醒挂起的流，执行工具 → 结果回填 → 继续 LLM 循环 → 流式输出最终答复
8. 若超时或取消 → 回填「用户取消」，让模型给出相应话术
```

### 技术要点（面试可讲）

- **挂起与唤醒**：用 `CompletableFuture` 或 `ConcurrentHashMap<messageId, SseEmitter>` 保存待确认的流，confirm 接口根据 messageId 唤醒
- **超时处理**：60 秒未确认则自动取消，避免连接泄漏
- **幂等**：同一条消息不能重复执行写操作，需要状态标记（PENDING → CONFIRMED / CANCELLED / TIMEOUT）
- **安全**：写操作仍需校验参数，且必须由用户在界面上显式确认，模型不能自行决定执行
