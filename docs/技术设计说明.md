# 技术设计说明

这份文档记录「为什么这么设计」，以及每个决策的替代方案是什么。
面试时被追问到的点，基本都在这里。

## 一、整体架构

```
┌──────────────────────────────────────────────────────────┐
│  前端 Vue3 + TS                                          │
│  ├── /chat   流式对话 + 引用溯源 + Agent 决策面板         │
│  └── /kb     知识库管理 + 召回测试                        │
└───────────────────────┬──────────────────────────────────┘
                        │  fetch + ReadableStream（SSE 手动解析）
┌───────────────────────▼──────────────────────────────────┐
│  Spring Boot 3                                            │
│  ┌────────────────────────────────────────────────────┐  │
│  │ controller   AuthController / ChatController / KbController │
│  ├────────────────────────────────────────────────────┤  │
│  │ ★ ChatService —— Agent 编排引擎                     │  │
│  │    检索 → Agent 循环（决策/工具/再决策）→ 收口 → 落库 │  │
│  ├──────────────┬──────────────┬──────────────────────┤  │
│  │ rag/         │ tool/        │ confirm/             │  │
│  │ 切片·检索    │ 工具注册执行 │ 写操作挂起唤醒        │  │
│  ├──────────────┴──────────────┴──────────────────────┤  │
│  │ LlmClient（DeepSeek）  EmbeddingClient（bge-m3）    │  │
│  └────────────────────────────────────────────────────┘  │
└───────────────────────┬──────────────────────────────────┘
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
  PostgreSQL 16 + pgvector        DeepSeek / 硅基流动 API
  （业务数据 + 向量 + 决策轨迹）
```

**为什么不用 Spring AI / LangChain4j**：

这两个框架的价值在于「快速接一个模型跑起来」，但这个项目要展示的恰恰是编排逻辑本身。
用框架的话，Agent 循环、工具注册、流式工具的解析全部被封装掉，面试时说不清里面发生了什么。
自研的成本也不高 —— `LlmClient` 只有 300 行，但它同时处理了流式、usage 统计、
工具调用分片聚合三件事，每一件都能展开讲。

**什么时候该用框架**：如果目标是两周内上线一个 RAG 应用，那 Spring AI 明显更划算。
这里不用它是因为项目目标是「展示对编排的理解」，不是「最快交付」。

## 二、RAG 检索链路

### 切片策略

`TextSplitter` 按「段落 → 句子 → 硬切」三级降级切分，目标长度 `chunk-size = 500`，
相邻切片保留 `chunk-overlap = 80` 字符重叠。

- **为什么按段落而不是定长切**：电商政策是「一条规则一段」的结构，
  按字符数硬切会把一条完整规则劈成两半，检索到半条等于没检索到。
  段落超长时才降级按句号切（语义基本完整），句子仍然超长才硬切（兜底，几乎不触发）。
- **为什么要重叠**：一个问题的答案可能横跨两段，重叠区保证边界信息不会丢。
- **为什么是 500 字**：太小则语义不完整，太大则一个切片里混进多个主题、相似度被稀释。

**可改进处**：目前是固定长度，进一步可以按标题层级切（Markdown 的 `##` 天然是语义边界），
或者对长文档先用 LLM 生成摘要再切。数据量上来后值得做。

### 检索效果实测

`scripts/eval-retrieval.py` 用 15 个标注问题（对应 8 篇政策文档）+ 4 个知识库外问题做评测：

**召回质量**（与阈值无关，衡量向量检索本身的排序能力）：

| 指标 | 结果 |
| --- | --- |
| Hit@1 | **15/15 = 100%** |
| Hit@3 | 15/15 = 100% |
| MRR | **1.0000** |
| 真问题 Top1 分数区间 | 0.632 ~ 0.813（平均 0.737） |

**阈值扫描**（阈值只决定哪些片段进 Prompt，不改变排序）：

| 阈值 | 答案覆盖率 | 噪声率 | 正确拒答率 |
| --- | --- | --- | --- |
| 0.30 | 100% | 75.3% | 0% |
| 0.35 ← 原配置 | 100% | 75.3% | 0% |
| 0.45 | 100% | 73.4% | 0% |
| 0.50 | 100% | 73.1% | 25% |
| **0.55 ← 现配置** | **100%** | **69.8%** | **100%** |
| 0.60 | 100% | 61.8% | 100% |

知识库外问题的最高得分集中在 **0.499 ~ 0.522**，而真问题 Top1 最低也有 **0.632** ——
两者在 0.55 附近有一条清晰的分界线。

**这就是把阈值从 0.35 调到 0.55 的依据**：正确拒答率从 0% 提升到 100%，
而答案覆盖率一点没掉。原先 0.35 的配置下，任何无厘头的问题都会召回一堆
0.4 分左右的不相关片段塞进 Prompt，模型只能硬着头皮编。

**这个案例本身比数值更有价值**：阈值不该拍脑袋定，它取决于「你的检索模型
在这批数据上的分数分布」——换向量模型、换文档集，这条线就变了，得重测。

### 混合检索该不该做：一次有结论的评测

「加一路关键词检索做混合」是被讲烂了的 RAG 优化建议。我没有直接照做，
而是先跑了评测（`scripts/eval-hybrid.py`），**结论是不做** —— 数据不支持为它增加复杂度。

做法：后端加一路纯 SQL 关键词检索（`pg_trgm` 的 `word_similarity`），
`GET /api/kb/search?mode=vector|keyword` 两路独立可调；
融合放在评测脚本里算，这样换融合策略不用反复改后端，也不动主链路的分数语义
（融合后的分数会失去「余弦相似度」的绝对含义，而阈值 0.55 是按那个量纲定的）。

**两套测试集是这个评测的关键** —— 只用一套会得出错误结论：

| 测试集 | 条数 | 设计意图 |
| --- | --- | --- |
| A · 同构问题 | 15 | 措辞贴近文档标题，看基本盘 |
| B · 口语化改写 | 8 | 字面与文档几乎不重合、语义相同，压测语义泛化 |

**A 组本身就是个陷阱**：两路都接近满分，会得出「关键词也不差」的错误结论 ——
天花板效应把真实差距全盖住了。能分辨高下的是 B 组。

| 策略 | A 组 Hit@1 | A 组 MRR | B 组 Hit@1 | B 组 MRR |
| --- | --- | --- | --- | --- |
| 纯向量 | 100.0% | 1.0000 | **87.5%** | **0.9000** |
| 纯关键词 | 53.3% | 0.7556 | 37.5% | 0.4625 |
| RRF 等权融合 | 100.0% | 1.0000 | 50.0% | 0.6135 |
| RRF 加权融合 (.8/.2) | 100.0% | 1.0000 | 50.0% | 0.6604 |

**等权融合反而伤害了向量通道**（B 组 MRR 0.9000 → 0.6135）。
逐条看明细，受损的样本全是「向量排第 1、融合后掉到 3~5」这一类。

#### 掉分的机制可以推导出来

RRF 的分数是 `Σ w/(k+rank)`。在这个场景里发生的事是：

```
向量第 1 名      w_v/(k+1)
两路共识候选      w_v/(k+2) + w_k/(k+1)      ← 向量第 2 名，同时被关键词通道召回
```

后者反超前者的条件解出来是 **`w_k > w_v/(k+2)`**，k=60 时即 **1.6%**。

实测正好卡在这条线的两侧：

| 权重（向量/关键词） | B 组 MRR | 说明 |
| --- | --- | --- |
| 1.00 / 0.00 | 0.9000 | 纯向量基线 |
| 0.99 / 0.01 | 0.9000 | 未越过 1.6%，持平 |
| 0.98 / 0.02 | 0.8375 | 越过去了，开始掉 |
| 0.90 / 0.10 | 0.6604 | |
| 0.80 / 0.20 | 0.6604 | |
| 0.70 / 0.30 | 0.6604 | |
| 0.60 / 0.40 | 0.6604 | |
| 0.50 / 0.50 | 0.6135 | |

**所以「调权重」在这里是个伪选项**：任何真正能起作用的权重（≥0.1）都远在临界线之上。
根因是当一路信号明显更强时，RRF 的「共识奖励」奖励的是噪声而不是信号。

顺带一个反直觉的观察：`k` 这一维完全没有区分度，10 / 30 / 60 / 100 全部得 0.6135。
因为等权时 k 只是把「名次差」整体缩放，不改变两路之间的话语权比例。
**反过来说：调 k 解决不了等权融合的问题，得调权重；而这个场景里权重也救不了。**

#### 那关键词通道为什么还留着

理由不是精度：

1. **快** —— 平均 4.4ms，而向量通道实测 197~362ms（波动来自外部 Embedding API），差近两个数量级
2. **是唯一的退路** —— Embedding 服务不可用时它还能用，且完全不依赖外部网络
3. **稀有精确串本来就是向量模型的弱项** —— 订单号、型号、SKU 这类内容关键词更靠谱。
   但本知识库全是政策文档，没有这类内容，所以这条优势在这里根本测不出来

最终处理：**主链路保持纯向量，关键词通道保留为可切换的降级通道**
（`/api/kb/search?mode=keyword`），与 KbView 的召回测试共用同一个入口。

#### 这个评测的价值

它展示的是一个判断过程而不是一个功能：**「别人说好」不等于「我的数据上也好」**，
而能做出判断的前提，是先有一个能分辨高下的测试集。
如果只做 A 组，我会得出「两路差不多，加起来试试」的错误结论，然后把它写进简历。

（诚实说明：B 组只有 8 条，上面扫出来的权重数字不该当作选参依据 ——
样本量不够。它在这里的用途是验证机制推导，不是调参。）

### 向量化

调用硅基流动 `BAAI/bge-m3`，1024 维。

**一个容易被忽略的坑**：`/v1/embeddings` **不保证返回顺序与输入一致**。
`EmbeddingClient` 按每条返回的 `index` 字段重排，不排会导致切片与向量错位。
这种 bug 不会抛异常，只会让检索结果变得莫名其妙 —— 是最难排查的一类问题。

### pgvector 集成

- `PgVectorTypeHandler` 做 `float[]` ↔ `vector` 互转
- 检索用 `<=>` 余弦距离，排序后转相似度 `1 - distance`

**一个实际踩到的设计选择**：查询时不用 TypeHandler 传参，而是把向量拼成
`'[0.1,0.2,...]'::vector` 字符串字面量。原因是 JDBC 的 `setObject` 对 `vector`
这类自定义类型的支持在各版本驱动上不一致，字符串 + 显式类型转换是最稳的写法。
代价是放弃了预编译的参数化（但向量本身不是用户输入，没有注入风险）。

JDBC URL 上的 `stringtype=unspecified` 是个一石二鸟的参数：
它同时解决了 `jsonb`（citations / trace 列）和 `vector` 的类型转换问题。

### 阈值：一个必须放在 Prompt 组装处的判断

**这是整个 RAG 部分最重要的一个设计决定。**

阈值过滤**不放在检索层**，而是放在 Prompt 组装处：

```java
// RetrievalService 返回全部 topK 命中，每条带分数
List<ChunkHit> hits = retrievalService.search(question, null);

// ChatService 组装 Prompt 时才按阈值筛
private List<ChunkHit> usedHits(List<ChunkHit> hits) {
    double threshold = retrievalService.getScoreThreshold();
    return hits.stream().filter(h -> h.score() >= threshold).toList();
}
```

同时，`rag` 事件把**全部命中**推给前端，每条带 `used` 标记。

**为什么值得这么麻烦**：模型回答「我查不到相关政策」时，有两种完全不同的原因 ——

1. 检索确实没召回相关内容（检索问题，要改切片或向量模型）
2. 召回了但分数不够被丢弃（阈值问题，或那条内容本来就不相关）

如果检索层直接把低分结果扔掉，这两种情况在观测上完全一样，无法区分。
把过滤推迟到最后一刻，决策面板就能显示「命中 5 条，采用 0 条」，
一眼看出是第 2 种情况。

`GET /api/kb/search` 这个「只检索不进模型」的接口也是同一个思路：
调参时需要一个不受模型输出干扰的观测面。

## 三、Agent 循环

### 为什么用流式工具调用，而不是「先非流式决策，再流式生成」

一个朴素实现是：
1. 先发一次**非流式**请求，看模型是否要调工具（非流式才能拿到完整的 `tool_calls`）
2. 调工具
3. 再发一次**流式**请求生成最终回答

这样代码简单，但**每一个不需要工具的普通问答，都会白白多一次非流式往返**。
首 token 延迟直接翻倍 —— 而首 token 延迟恰恰是流式体验里最关键的指标。

所以这里选择**在流式请求里直接带 `tools`**，自己解析分片。

### 流式工具调用的解析

实测 DeepSeek 的返回格式（标准 OpenAI 协议）：

```
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_xxx","type":"function",
        "function":{"name":"query_logistics","arguments":""}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{"}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"\""}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"order"}}]}}]}
...
data: {"choices":[{"delta":{"content":""},"finish_reason":"tool_calls"}]}
data: [DONE]
```

关键点：

- 第一片给出 `index` / `id` / `name`，后续每片**只给一小段 `arguments`**
- 必须按 `index` 归组，把 `arguments` **顺序拼接**才能还原成合法 JSON
- `finish_reason: "tool_calls"` 表示本轮是工具调用而非最终回答

`LlmClient.ToolCallAccumulator` 负责这件事。用 `LinkedHashMap` 而不是 `HashMap`，
因为模型给出的 `index` 顺序就是它期望的执行顺序。

### 多步循环与兜底

```
for (int step = 1; step <= MAX_AGENT_STEPS; step++) {
    List<ToolCall> toolCalls = llmClient.streamChat(messages, tools, ...);
    if (toolCalls.isEmpty()) break;           // 模型不再要工具 → 本轮即最终回答

    messages.add(LlmMessage.assistantToolCalls(toolCalls));   // 记录调用意图
    for (ToolCall call : toolCalls) {
        executeTool(call, ...);               // 执行 + 把 tool 消息回灌
    }
}

// 兜底：跑满步数仍在调工具 → 去掉 tools 强制生成
if (!finished && answer.isEmpty()) {
    llmClient.streamChat(messages, null, ...);
}
```

两个细节值得说：

1. **步数上限 5 步**。这是防「模型反复调同一个工具」的死循环。
   上限不能太小（正常对话可能需要「查订单 → 查物流 → 回答」三步），也不能太大
   （每步都是一次模型调用，成本和时间都线性增长）。
2. **兜底强制生成**。如果跑满步数还在调工具，直接结束会得到一条
   「有工具日志但没有回答」的空白消息，用户体验极差。
   去掉 `tools` 再跑一次，逼它基于已有信息给出文字回答。

### 工具的 memory 语义

工具执行结果以 `role: "tool"` 的消息回灌，必须带 `tool_call_id` 指回是哪一次调用：

```java
messages.add(LlmMessage.tool(call.id(), result.toModelContent()));
```

而 `tool` 消息的 `content` 不是原始数据，是 `ToolResult.toModelContent()` 裁剪过的摘要：

```json
{"success": true, "summary": "订单 xxx 最新物流：已签收", "data": {...}}
```

**为什么不把整坨数据塞回去**：一次查询可能返回 8 条物流轨迹，
原始 JSON 上千 token，全塞进上下文既费钱又会稀释重点。
摘要 + 结构化数据的分工，让模型拿到结论，让前端拿到明细。

### 失败也是合法结果

工具失败时不抛异常中断对话，而是返回 `{"success": false, "error": "..."}`：

```java
if (order == null) {
    return ToolResult.fail("订单号 " + orderNo + " 不存在，请确认后重新提供");
}
```

这样模型知道「这个工具失败了」，可以换个方式回答或引导用户，
而不是整轮对话直接报错。这个设计在场景 3 的复测里体现得很明显 ——
订单已经是「退款中」时，`apply_refund` 返回业务规则拒绝，
模型据此回答「该订单已在退款中，无需重复申请」，体验是连贯的。

## 四、写操作二次确认（项目里最复杂的一块）

### 问题定义

一个写操作（申请退款、改地址）不能让 Agent 直接执行 —— 必须用户点头。
但此时 SSE 流已经建立，Agent 正处在循环中间。

难点：**「挂起」和「唤醒」发生在两个完全独立的 HTTP 请求里。**

- 请求 A：`POST /api/chat/stream` —— 长连接，推流线程阻塞在这里
- 请求 B：`POST /api/chat/confirm` —— 用户点击确认时发出的新请求

两者之间没有任何天然的关联（不同的连接、不同的线程）。
唯一可行的办法是**在进程内维护一个注册表**，用 `confirmId` 把它们接起来。

### 实现

```java
// 推流线程侧（ChatService.executeTool）
PendingConfirm pending = confirmRegistry.register();
send(emitter, "tool_confirm", Map.of("confirmId", pending.getId(), "preview", ...));
PendingConfirm.Status status = pending.await(60);      // ← 阻塞在这里
confirmRegistry.remove(pending.getId());

// HTTP 请求侧（ChatController.confirm）
boolean accepted = confirmRegistry.resolve(confirmId, approved);
```

`PendingConfirm` 用一次 CAS 同时解决三个边界：

```java
public boolean resolve(boolean approved) {
    Status target = approved ? Status.CONFIRMED : Status.CANCELLED;
    if (!status.compareAndSet(Status.PENDING, target)) {
        return false;          // 已超时或重复点击 → 丢弃
    }
    latch.countDown();
    return true;
}

public Status await(long timeoutSeconds) throws InterruptedException {
    boolean finished = latch.await(timeoutSeconds, TimeUnit.SECONDS);
    if (!finished) {
        status.compareAndSet(Status.PENDING, Status.TIMEOUT);   // 超时也让流程继续
    }
    return status.get();
}
```

| 边界情况 | 处理方式 |
| --- | --- |
| **超时** | `latch.await(60, SECONDS)` 超时返回 false，CAS 置 TIMEOUT，推流线程继续往下走。**不能让线程永久占住** —— 线程池只有 16 个，几个用户挂机就能把服务拖垮 |
| **重复点击** | 只有第一次 CAS 成功。第二次返回 `accepted: false`，接口层回「已失效」 |
| **迟到回执** | 已超时后用户才点，CAS 失败 → 不会偷偷把状态改成 CONFIRMED。这个顺序保证很重要：**一旦判定超时，就不能再被推翻** |
| **SseEmitter 超时** | 构造时传 `0L` 表示不超时，否则默认超时会在用户思考时把流掐断 |

### 状态机

```
        用户点确认
PENDING ──────────→ CONFIRMED ──→ 执行工具
   │
   ├──── 用户点取消 ─→ CANCELLED ──→ 回灌「用户取消了」，不执行
   │
   └──── 60s 无响应 ─→ TIMEOUT   ──→ 回灌「超时自动取消」，不执行
```

### 取消后必须明确告诉模型「不要再试」

```java
messages.add(LlmMessage.tool(call.id(),
    "{\"success\":false,\"error\":\"" + reason +
    "。请直接告知用户操作已取消，不要再次尝试调用该工具。\"}"));
```

不加这句，模型很可能原地再发起一次同样的调用，然后又被拒绝，白白烧两轮 token。
这是实测踩出来的 —— **给模型的错误信息里要包含「下一步该做什么」，而不只是「哪里错了」**。

### 已知限制与演进

**当前实现是单实例的**：`ConfirmRegistry` 用 `ConcurrentHashMap` 存在进程内存里。

多实例部署下会出问题：用户点确认的请求可能被负载均衡打到**另一台机器**上，
那台机器上没有这个 `confirmId`，回执直接失效。

要支持多实例，必须改成：

```
Redis 存 pending 状态 + 发布订阅做唤醒
  ├─ 推流线程：SETEX confirm:{id} PENDING 60，SUBSCRIBE confirm:result:{id}
  ├─ 确认请求：SET 状态 + PUBLISH 唤醒消息
  └─ 这样任意实例都能处理回执
```

**这是面试里最值得主动说的一个限制** —— 主动指出自己方案的边界，
比声称「我这个设计很完美」可信得多。

## 五、可观测性设计

这个项目的差异化在于**把 Agent 的黑盒打开**。

### 三层观测面

| 层 | 手段 | 用途 |
| --- | --- | --- |
| 实时 | SSE 事件（`rag` / `tool_call` / `tool_confirm` / `tool_result`） | 前端决策面板实时展示 |
| 事后 | `chat_message.trace`（jsonb） | 回放任意一轮的完整决策轨迹 |
| 调参 | `GET /api/kb/search` | 只跑检索不进模型，隔离模型输出干扰 |

### trace 的结构

```json
{
  "useRag": true,
  "retrieveMs": 614, "topK": 5, "threshold": 0.35,
  "hitCount": 5, "usedCount": 5,
  "llmMs": 4218, "promptTokens": 7019, "completionTokens": 417,
  "model": "deepseek-chat",
  "agentSteps": 3, "toolCallCount": 2,
  "tools": [
    {"step":1,"tool":"query_order","write":false,"success":true,"summary":"...","ms":6},
    {"step":2,"tool":"apply_refund","write":true,"confirm":"CONFIRMED","success":true,"ms":13}
  ]
}
```

### 耗时为什么要拆三段

`retrieveMs`（检索）+ `firstTokenMs`（发起模型请求到首个 token）+ `totalMs`（含检索）

用户感知的「慢」可能来自完全不同的地方：

- `retrieveMs` 高 → 检索问题（向量计算慢、数据量大、需要加索引）
- `firstTokenMs` 高 → 模型首字延迟（prompt 太长、模型负载、网络）
- `totalMs - llmMs` 高 → 检索在总耗时里占比大

不拆开就只能看到「一共用了 2 秒」，无法定位。

### 实测数据（8 篇文档 / 20 个切片）

| 场景 | 检索 | 首 token | 总耗时 | 决策轮数 | 工具次数 |
| --- | --- | --- | --- | --- | --- |
| 纯政策问答 | 614ms | 518ms | 2237ms | 1 | 0 |
| 查物流 | 191ms | 1650ms | 2324ms | 2 | 1 |
| 申请退款（含确认） | 236ms | 621ms | 4465ms | 3 | 2 |

**读法**：查物流的首 token 明显更高（1650ms vs 518ms），是因为要等模型先决定调工具、
再等工具执行、再进入第二轮生成。这个延迟是 Agent 多步决策的固有成本 ——
**多步能力的代价就是首字延迟**，这是必须向用户交代的取舍（前端可以用「正在查询订单…」的状态提示来缓解）。

## 六、前端实现要点

### 为什么不用 EventSource

`EventSource` 只支持 GET，参数只能塞进 URL。这个项目需要传：

- 多轮上下文的 `sessionId`
- 两个实验开关（`useRag` / `enableTools`）
- 后续还要支持确认回执

所以用 `fetch` + `ReadableStream` 手动解析 SSE。

### SSE 解析的两个坑

**坑一：中文被切在 chunk 边界上。** UTF-8 下一个汉字占 3 字节，
一次 `read()` 返回的 chunk 很可能把某个汉字劈成两半。

```js
// ❌ 会出乱码
const text = new TextDecoder().decode(value)

// ✅ stream: true 让解码器保留跨 chunk 的不完整字节
buffer += decoder.decode(value, { stream: true })
```

**坑二：事件边界。** SSE 以空行分隔事件，但最后一次 `read()` 的内容可能
不包含结尾的空行，循环结束后需要再 flush 一次 buffer。

### 引用角标的渲染

模型输出的 `[1]` 需要渲染成可点击的角标。顺序很关键：

```js
const rendered = marked.parse(source)          // 先 markdown
const safe = DOMPurify.sanitize(rendered)      // 再净化
return safe.replace(/\[(\d+)\]/g, '<sup class="cite-badge">$1</sup>')
```

- **顺序不能反**：先净化会把 markdown 语法一起干掉
- **替换放在净化之后**：插入的是自己生成的固定标签 + `\d+` 捕获组，不含外部输入，安全
- 引用来源明细不依赖模型输出，而是从 `rag` 事件里筛 `used: true` 的命中 —— 
  这样即使模型忘记标角标，来源列表依然准确

### 消息气泡不更新：一个 Vue3 响应式陷阱

浏览器走查时发现 AI 回复的气泡永远停在「正在输入」，但右侧决策面板一切正常。

```js
// ❌ 气泡永远停在加载态
const reply = { id, role: 'ASSISTANT', content: '', streaming: true }
messages.value.push(reply)
reply.content += text          // 改的是原始对象，不是数组里的代理
```

`messages.value` 是 `ref` 数组，push 进去的对象会被 `reactive()` 包一层代理并缓存。
模板读的是**代理**，闭包里的 `reply` 指向的却是**原始对象** —— 绕过代理直接改属性，
依赖收集不到，视图自然不更新。

```js
// ✅ 把代理取回来用
messages.value.push({ id, role: 'ASSISTANT', content: '', streaming: true })
const reply = messages.value[messages.value.length - 1]
reply.content += text
```

**「一半正常一半不正常」本身就是定位线索**：`rag` / `tools` / `done` 是独立的 `ref`，
改的是 `.value`，走的是正常响应式路径，所以面板没问题。如果是接口或 SSE 的问题，
两块都该是空的。

这类 bug **类型检查抓不到、构建也不报错**，只有在真实浏览器里跑一遍才看得见 ——
这也是 `scripts/ui-check.mjs` 存在的意义：它不只是截图工具，
是唯一能覆盖「渲染」这一层的手段。

## 七、如果继续做下去

按优先级排序，都是「已经知道该怎么做，只是当前不值得做」的：

| 方向 | 具体做法 | 为什么现在不做 |
| --- | --- | --- |
| **混合检索** | 向量检索 + BM25 关键词检索，用 RRF 融合排序 | 对「退款」「运费」这类术语型查询提升明显，但要引入 ES 或 pg 全文索引，工程量翻倍 |
| **Rerank** | 召回 top20 后用 rerank 模型精排到 top5 | 效果提升最直接，但多一次 API 调用，延迟 +200ms |
| **切片优化** | 按 Markdown 标题层级切，而非固定长度 | 需要先有更大更杂的文档集才能体现价值 |
| **多实例支持** | `ConfirmRegistry` 换 Redis + 发布订阅 | 演示项目单实例足够，但这是明确的扩展点 |
| **评测体系** | 已有的 `eval-retrieval.py` 扩展成 CI 门禁 | 需要先有一批真实的线上问题做标注 |
| **成本优化** | 语义缓存（相似问题命中缓存）、Prompt 压缩 | 当前数据量下没有优化空间 |

## 八、面试高频问题准备

**Q：你这个 Agent 和「RAG 问答机器人」的区别是什么？**

A：区别在于「模型是否自己做决策」。纯 RAG 的流程是固定的：检索 → 拼 prompt → 生成，
模型没有选择权。这个项目里模型要自己判断：这个问题需不需要查订单？需要调哪个工具？
参数是什么？拿到结果后还要判断是否够了、要不要再查一次。
具体体现在 `agentSteps=3, toolCallCount=2` 这种多步轨迹上 —— 同样一个问题，
模型可能先查订单再查物流，也可能直接回答，这个选择是它做的。

**Q：怎么防止模型乱调工具？**

A：三层。① 工具描述里写清使用场景和前置条件，比如 `query_order` 明确写
「如果用户没有提供订单号，不要调用本工具，先向用户索要」；② JSON Schema 里
`required` 标注必填、`additionalProperties: false` 拒绝多余字段；
③ 执行前做参数校验，缺参数返回明确的失败信息让模型重新决策。
另外所有工具调用都会记录到 trace，出问题可以回放。

**Q：模型调工具失败怎么办？**

A：不抛异常中断，而是把失败作为工具结果回灌给模型，
让它可以换方式回答。比如订单不存在时，模型会说「没查到这个订单，请确认订单号」，
而不是给用户一个报错页面。

**Q：如果模型陷入死循环反复调工具？**

A：`MAX_AGENT_STEPS = 5` 硬上限。跑满之后会去掉 tools 再跑一次，
强制它基于已有信息生成文字回答 —— 保证用户至少能拿到一个可读的结果，
而不是一条没有回答的空白消息。

**Q：SSE 流挂起等用户确认，用户不点怎么办？**

A：60 秒超时，`CountDownLatch.await(timeout)` 返回 false 后自动置 TIMEOUT 继续往下走。
关键是**不能永久阻塞推流线程** —— 线程池只有 16 个，几个人挂机就能把服务拖垮。
超时/取消后会把「操作已取消」回灌给模型，并明确要求它不要再重试。

**Q：用户连点两下确认呢？**

A：`AtomicReference` 的 CAS 保证只有第一次回执生效，第二次直接返回 `accepted: false`。
超时后再点也一样 —— 一旦判定超时就不能被推翻。这个顺序保证比「谁最后写谁赢」安全得多。

**Q：为什么不用 LangChain4j / Spring AI？**

A：这个项目的目的是展示对编排逻辑的理解，用框架会把 Agent 循环、
流式工具解析、工具注册这些恰好最有价值的部分封装掉。
自研的成本其实不高（`LlmClient` 300 行），而且能讲清楚里面每一处为什么这么写。
但如果是两周内要交付一个 RAG 应用，我会直接用框架 —— 那是不同的目标函数。
